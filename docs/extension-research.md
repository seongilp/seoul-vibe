## 과제 1 — 실시간 상권 (`LIVE_CMRCL_STTS`)

121곳 전부에 대해 `citydata` 를 1회씩 호출해 `LIVE_CMRCL_STTS` 만 추출했다 (동시 8). 결과는 `data/raw/cmrcl-121.json`.

### 1.1 데이터가 나오는 장소

| 구분 | 수 |
| --- | --- |
| `LIVE_CMRCL_STTS` 가 객체로 오는 장소 | **82 / 121** |
| `LIVE_CMRCL_STTS` 가 `null` 인 장소 | **39 / 121** |

10:40 과 11:06 두 번 조회했고 **같은 39곳이 두 번 모두 `null`** 이었다. 일시적 결측이 아니라 구조적이다.

`null` 인 39곳의 분류:

| 카테고리 | null / 전체 |
| --- | --- |
| 공원 | **33 / 33 (전부)** |
| 고궁·문화유산 | 3 / 5 (경복궁, 서울 암사동 유적, 창덕궁·종묘) |

해석: 카드 가맹점이 사실상 없는 폴리곤이다. 공원·한강공원·산·궁궐이 전부 빠졌다. **"발달상권"과 "관광특구"는 100% 커버**되므로 상권 탭을 붙이기에는 오히려 잘 맞는다.

### 1.2 `AREA_CMRCL_LVL` 값의 집합

인구 혼잡도(`여유/보통/약간 붐빔/붐빔`)와 **문자열이 다르다.** 4단계인 것은 같다.

| 값 | 관측 장소 수 (2026-08-30 10:40, 토요일 오전) |
| --- | --- |
| 한산한 | 58 |
| 보통 | 21 |
| 바쁜 | 2 |
| 분주한 | 1 |

`RSB_PAYMENT_LVL`(업종별 레벨)도 같은 4개 값만 쓴다 (한산한 184 / 보통 39 / 분주한 16 / 바쁜 15).

**순서는 문서로 확인하지 못했다.** 서울 열린데이터광장 데이터 정의서에서 정렬 순서를 찾지 못했으므로, 데이터로 추정했다. 같은 업종중분류 안에서 `RSB_SH_PAYMENT_CNT / RSB_MCT_CNT`(가맹점당 결제건수) 중앙값을 보면:

| 업종 | 한산한 | 보통 | 바쁜 | 분주한 |
| --- | --- | --- | --- | --- |
| 편의점 | 0.252 | 0.404 | 0.542 | 0.562 |
| 제과/커피/패스트푸드 | 0.146 | 0.182 | 0.229 | 0.311 |
| 전체 | 0.110 | 0.316 | 0.234 | 0.487 |

두 업종 모두에서 단조증가하므로 **`한산한 < 보통 < 바쁜 < 분주한`** 으로 본다. 전체 집계에서만 보통/바쁜이 뒤집히는데 업종 구성 차이 때문이다. → **추정이다. 확정하려면 정의서 확인 필요.**

또 하나: **레벨은 절대 결제건수의 함수가 아니다.** 명동 관광특구는 결제건수 470건(전체 1위)인데 `보통` 이고, 가락시장은 24건인데 `분주한` 이다. 인구 혼잡도와 마찬가지로 **그 장소 자체의 평소 대비 상대값**으로 보인다. 장소끼리 레벨을 직접 비교해 랭킹을 만들면 안 된다.

### 1.4 시각 필드 두 개 — 성격이 다르다

| 필드 | 예시 값 | 의미 | 실시간? |
| --- | --- | --- | --- |
| `CMRCL_TIME` | `20260830 1040` | 상권 집계 기준 시각. 조회 시각과 거의 일치했다 (82곳 중 73곳이 동일 값, 최대 편차 약 2시간). | **예** |

→ `RSB_MCT_CNT`("가맹점 25곳")를 실시간 값처럼 붙이면 안 된다. UI 에 쓴다면 `2026년 7월 기준` 같은 라벨이 반드시 필요하다.

### 1.5 필드 목록과 타입

`AREA_SH_PAYMENT_CNT` 만 문자열이고 나머지 수치는 JSON number 로 온다. 타입이 섞여 있으니 파싱에 주의.

| 필드 | 타입 | 관측 범위 / 비고 |
| --- | --- | --- |
| `AREA_CMRCL_LVL` | string | 4단계 |
| `AREA_SH_PAYMENT_CNT` | **string** | 4 ~ 470, 중앙값 20 |
| `AREA_SH_PAYMENT_AMT_MIN` / `_MAX` | number | 10,000 ~ 3,300,000 |
| `CMRCL_MALE_RATE` / `_FEMALE_RATE` | number | 합계 100.0 |
| `CMRCL_10_RATE` ~ `CMRCL_60_RATE` | number | 합계 99.9~100.0 (반올림 오차) |
| `CMRCL_PERSONAL_RATE` / `_CORPORATION_RATE` | number | 합계 100.0 |
| `CMRCL_TIME` | string | `YYYYMMDD HHMM` |
| `CMRCL_RSB` | array | 1~8건 |

### 1.6 결제금액은 구간값이다

`AREA_SH_PAYMENT_AMT_MIN`~`MAX` 는 정확한 금액이 아니라 **구간**이다. 구간 폭의 분포:

| 구간 폭 | 장소 수 |
| --- | --- |
| 10,000원 | 22 |
| 50,000원 | 49 |
| 100,000원 | 11 |

즉 금액대에 따라 구간 폭 자체가 달라진다. 인구수(`AREA_PPLTN_MIN/MAX`)와 같은 처리 — 중앙값 하나로 뭉개지 말고 `7~8만원` 처럼 범위 그대로 보여주는 게 맞다. 합계·평균 같은 산술 연산은 의미가 없다.

### 2.3 혼잡도의 단위·척도

**퍼센트(%)** 다. 등급도 명수도 아니다.

| 통계 | 값 |
| --- | --- |
| 관측치 수 | 65,169 |
| 최솟값 | 0.0 |
| 중앙값 | 25.7 |
| 95퍼센타일 | 64.6 |
| 최댓값 | **147.7** |
| 100 초과 비율 | 0.63% |

100 을 넘는 값이 존재하므로 비율(정원 대비 승차인원)이 맞다. 100% = 정원. `15119451` PDF 의 각주도 같은 정의를 쓴다("첨두시 혼잡도(%)"). 서울교통공사 기준으로 100%는 좌석+입석 정원(1칸 약 160명)이다 — **이 정원 환산 수치는 확인 필요.**

UI 로 옮길 때 0~150 을 그대로 게이지에 매핑하면 대부분의 셀이 25% 근처에 몰린다. 4단계 구간화(예: ~40 여유 / ~80 보통 / ~120 혼잡 / 120~ 매우혼잡)를 두는 편이 인구 혼잡도 UI 와도 맞다. **구간 경계는 임의 제안이며 공식 기준이 아니다.**

### 2.4 두 데이터 조인 — 결론: 조인할 대상이 아니다

`15119451` 이 부존재 통보 PDF 이므로 **서울교통공사 ↔ 한국철도공사 조인 자체가 성립하지 않는다.** 원래 의도였던 "겹치는 역 확인"은 무의미하다.

참고로 담당 노선은 실제로 겹치지 않는다. `15071311` 은 1~8호선 서울교통공사 구간만 담고 있고 (9호선·경의중앙·수인분당·신분당·공항철도 전부 없음), PDF 는 코레일 광역전철 노선(경부/경인/경원/안산/중앙/일산/분당/경의/경춘/수인/경강/동해)만 다룬다. 1호선은 서울역~청량리 지하구간(서울교통공사)과 코레일 구간이 분리 운영되므로 역 단위로도 겹치지 않는다.

### 2.6 진짜 "실시간" 지하철 데이터는 이미 받고 있다

data.go.kr 을 뒤져도 실시간 역별 혼잡도 API 는 찾지 못했다. 대신 `citydata` 에 이미 들어 있다:

| 키 | 내용 | 121곳 커버리지 |
| --- | --- | --- |
| `LIVE_SUB_PPLTN` | 장소 주변 지하철 실시간 승하차 인원 | **121 / 121** |
| `SUB_STTS[].SUB_DETAIL` | 역별 실시간 열차 도착정보 | 96 / 121 |

`LIVE_SUB_PPLTN` 필드 (홍대 관광특구 예):

| 필드 | 값 | 의미 |
| --- | --- | --- |
| `SUB_ACML_GTON_PPLTN_MIN/MAX` | 14900~15000 | 누적 승차 |
| `SUB_ACML_GTOFF_PPLTN_MIN/MAX` | 15700~15800 | 누적 하차 |
| `SUB_30WTHN_GTON/GTOFF_…` | 2200~2300 / 3700~3800 | 최근 30분 |
| `SUB_10WTHN_…` | 650~700 / 1200~1300 | 최근 10분 |
| `SUB_5WTHN_…` | 250~300 / 450~500 | 최근 5분 |
| `SUB_STN_CNT` | 8 | 집계에 포함된 역 수 |
| `SUB_STN_TIME` | `20260830` | **날짜만. 시:분이 없다.** |

인구·상권과 마찬가지로 **전부 MIN~MAX 구간값**이다. 100명 단위로 반올림돼 있다.

`15071311` 통계와 조합하면 "지금 최근 10분 승하차 N명 (평소 이 시간대 혼잡도 42%)" 같은 표현이 가능하다. `LIVE_SUB_PPLTN` 은 장소 단위 집계이고 `15071311` 은 역 단위이므로, 역 단위로 맞추려면 `SUB_STTS` 의 역 목록으로 매핑해야 한다.

121장소에 붙은 역 인스턴스 221개 중 **196개(89%)** 가 `15071311` 의 역명과 매칭된다. 매칭 실패 25개는 전부 서울교통공사 관할이 아닌 노선이다 (9호선 12, 수인분당 4, 신림선 3, 신분당 2, 경의중앙 2, 공항철도 1, 7호선 1).

## 함정

1. **`15119451` 은 데이터가 아니다.** 제목은 "지하철 역사 기준 칸 혼잡도"인데 받아지는 건 한국철도공사의 **정보부존재 통보 PDF** 한 장이다. 확장자도 거짓말이다 (`.hwpx` 인데 실제로는 PDF 1.6). 다운로드 성공 = 데이터 확보가 아니다.

2. **좌표 CSV(15099316)의 6호선 역번호가 한 칸씩 밀려 있다.** 역번호로 조인하면 6호선 34개 역의 좌표가 전부 옆 역 것으로 붙는다.

   | 역번호 | 혼잡도 CSV | 좌표 CSV |
   | --- | --- | --- |
   | 2614 | 독바위 | 독바위 |
   | **2615** | **연신내** | **봉화산** (경도 127.091 — 실제 봉화산 위치) |
   | 2616 | 구산 | 연신내 |
   | … | (한 칸씩) | … |
   | 2648 | 봉화산 | 화랑대 |
   | 2649 | 신내 | 신내 |

   좌표 CSV 의 *역명↔좌표* 쌍은 맞고 **역번호만 틀렸다**. 6호선 실제 체계(2615 연신내, 2648 봉화산)를 따르는 쪽은 혼잡도 CSV 다. → **역번호가 아니라 역명으로 조인하라.** 최소한 6호선은 반드시 역명 조인.

   불일치 총 41건 중 6호선이 34건이고, 나머지 7건은 단순 표기/개명 차이다: `서울역↔서울`, `신촌(지하)↔신촌`, `불암산↔당고개`(2024 개명), `강동(하남검단산)↔강동`, `올림픽공원(한국체대)↔올림픽공원`, `자양(뚝섬한강공원)↔뚝섬유원지`(개명, 좌표 동일), `이수↔총신대입구`.

3. **역명 표기가 세 데이터에서 다 다르다.** `citydata` 는 `서울`·`군자(능동)`, 혼잡도 CSV 는 `서울역`·`군자`. 괄호 제거 + `역` 접미사 정규화가 필요하다. 정규화 후 90개가 매칭되고, 남은 17개(`국회의사당`, `노량진`, `마곡나루`, `선정릉`, `신논현` 등)는 진짜로 서울교통공사 관할이 아닌 역이다.

4. **`15071311` 은 실시간이 아니다.** 2026-03-31 기준 시간대별 평균 통계다. UI 에서 실시간처럼 보이면 안 된다. 실시간이 필요하면 `LIVE_SUB_PPLTN`.

5. **`RSB_MCT_TIME` = `202607`.** 가맹점 수(`RSB_MCT_CNT`)는 2개월 전 월 단위 집계다. 나머지 상권 필드는 `CMRCL_TIME` 기준 실시간이다. 같은 카드 안에 섞어 놓으면 전부 실시간으로 읽힌다.

6. **상권 레벨 4단계의 문자열이 인구 혼잡도와 다르다.** 인구는 `여유/보통/약간 붐빔/붐빔`, 상권은 `한산한/보통/바쁜/분주한`. `congestionRank()` 를 재사용할 수 없다. 별도 배열이 필요하고, 순서(`한산한 < 보통 < 바쁜 < 분주한`)는 데이터로 추정한 값이지 문서로 확인한 게 아니다.

7. **상권 레벨은 장소 간 비교용이 아니다.** 명동(결제 470건) = `보통`, 가락시장(24건) = `분주한`. 각 장소의 평소 대비 상대값으로 보인다. 레벨로 랭킹을 만들면 틀린 순위가 나온다.

8. **공원 카테고리 33곳 전부가 상권 `null`.** 상권 탭을 무조건 렌더하면 3분의 1 가까운 장소에서 빈 카드가 뜬다. `null` 이면 탭 자체를 감추는 편이 낫다.

9. **`AREA_SH_PAYMENT_AMT` / `RSB_SH_PAYMENT_AMT` 는 '건당'이 아니라 '합계'다.**
   (2026-08-30 상권 탭 구현 중 확인, 위 1.6 을 정정한다.) 명동은 838건에 980~990만원인데
   건당으로 읽으면 총액이 82억이 된다. 82곳 전부에서 `금액 / 건수` 가 5,312원~82,558원
   (중앙값 22,859원)에 들어온다 — 이게 건당 단가다. 화면에 '건당'으로 라벨을 붙이면 안 된다.
   같은 조회에서 구간 폭은 10만원 52곳 / 5만원 25곳 / 1만원 5곳으로, 오전 스냅샷(1.6)과
   분포가 달랐다. 폭은 금액대에 따라 달라지므로 시간대마다 바뀐다.

10. **금액·인원이 전부 MIN~MAX 구간값.** 상권 결제금액은 구간 폭이 1만/5만/10만원으로 금액대마다 다르다. 지하철 승하차는 100명 단위. 중앙값으로 뭉개거나 합산하면 안 된다.

11. **CP949 인코딩.** `15071311`, `15099316`, `15099317` 전부 CP949 이고 BOM 이 없다. UTF-8 로 열면 첫 바이트에서 터진다.

12. **CSV 값에 후행 공백**이 있다 (`"8.0 "`, `"1호선"` 은 깨끗). 파싱 시 `strip()`.

13. **`SUB_STN_X` 가 경도, `SUB_STN_Y` 가 위도**다. GeoJSON 순서와 같지만 이름이 헷갈린다.

14. **`citydata` 는 무겁고 페이지네이션이 없다.** 장소당 약 170KB, `tm` 파라미터가 없어 잘라 받을 수 없다. 121곳 전수 조회 = 1회당 약 20MB. 상권을 붙일 때 상세 패널(이미 `citydata` 를 부르는 곳)에 얹으면 추가 호출이 0 이지만, 목록에 상권 배지를 뿌리려 하면 121콜이 추가로 필요해진다. `citydata_ppltn` 에는 상권 필드가 없다.

15. **data.go.kr 2단계 다운로드는 인증키가 필요 없지만 `publicDataDetailPk` 가 데이터셋마다 다르다.** 상세 페이지 HTML 의 `#publicDataDetailPk` input value 에서 긁어야 한다. `atchFileId` 는 재발급되므로 하드코딩하면 나중에 깨진다.
